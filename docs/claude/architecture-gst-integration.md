# Architecture: GST/ASP integration, async pattern, custom doctypes

**GST/ASP integration (`india_gst_api/`) is a thin API client layer** — `einv.py` (e-invoicing/IRN), `eway_bill_api.py` (e-way bill lifecycle), `gst_api.py`/`gst_public_api.py` (GSTIN verification) all call out to government-authorized ASP/GSP endpoints and write results back onto Sales Invoice / eWay Bill documents. Credentials are stored on `Rohit Settings` (not `Rohit GST Settings`, despite the name). `whitebooks_provider.py` owns the base URLs, the credentials, the reply envelope (`is_success`/`error_codes`/`unwrap`) and the authenticated e-Invoice and e-Way Bill clients (`einvoice_request`/`eway_request`). Use them; don't call `requests` directly for a new GST API.

**Vendor: WhiteBooks.in only.** Every GST API family is on WhiteBooks.in; the Charteredinfo/TaxPro code and its Rohit Settings fields were deleted. The integration is designed to line up with the shape `india-compliance` (the v14 successor app) expects, so the v14 upgrade doesn't require a second rewrite.
- Public GST (GSTIN search/return tracking, `gst_public_api.py`): since 2026-08-22.
- Taxpayer returns (GSTR1/GSTR2A/GSTR2B, per-GSTIN OTP `txn` session in `Rohit GST Settings`, `gst_api.py`): since 2026-10-27. The GST Network fetch on the GSTR1/GSTR2A doctypes runs as a background job.
- e-Invoice (`einv.py`) and e-Way Bill (`eway_bill_api.py`): since 2026-10-27 (#17, #19). They authenticate with the GSTIN's API user (`eway_bill_id`/`eway_bill_password`, or the sandbox GSTIN and user). On submit, a Sales Invoice is sent on the short queue; the 15-min sweep retries the ones it missed. `update_irn_details()` saves `irn`, `ack_no`, `ack_date` and `signed_qr_code`, and the print formats draw the QR from `signed_qr_code` (no PNG). `Rohit Settings.auto_generate_ewb_from_irn` also makes the e-Way Bill from the IRN. A developer_mode site always uses the sandbox for both. Some reply details are still UNVERIFIED until `whitebooks_sandbox_probe.run` is run on the sandbox; see the module notes.
- `test_only_whitebooks.py` fails if Charteredinfo markers come back.

**Async/background pattern**: heavy operations (invoices with ≥10 line items, e-invoice submission, address ERP sync) are queued rather than run inline, via `utils/background_doc_processing.py` and the `scheduled_tasks/` jobs, to avoid Desk request timeouts. Follow this pattern for any new operation that could be slow or hit an external API during a user-facing save/submit.

**Custom DocTypes** live under `rohit_common/rohit_common/doctype/`; validation *logic* for both custom and standard (core ERPNext) DocTypes is centralized in `rohit_common/rohit_common/validations/`, separate from the DocTypes it validates — don't look for validation code next to a standard DocType's own files, it isn't there.
