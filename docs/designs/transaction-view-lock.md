# Design: Transaction View-Lock (period close, read restriction)

Generated by /office-hours on 2026-08-21
Branch: version-13
Repo: rohit_common (Rohit Industries Group)
Status: DRAFT
Mode: Intrapreneurship

## Problem Statement

Users below a designated role can currently open, list, print, and pull into
reports any accounting transaction (Sales Invoice, Journal Entry, GL Entry,
and related doctypes) regardless of its date. There's no way to say "once a
period is closed, ordinary users can no longer even *see* what's in it" —
only a designated role should retain read access to pre-lock-date data.

## Status Quo

ERPNext already ships a **date-based edit/cancel lock**:
`Accounts Settings.acc_frozen_upto` (date) + `Accounts Settings.frozen_accounts_modifier`
(role). Enforced in `erpnext/accounts/general_ledger.py:check_freezing_date` —
blocks create/update/cancel of GL Entries (and the invoices/journal entries
that generate them) dated on/before the frozen date, for anyone without the
modifier role. Notably it deliberately excludes Administrator from bypassing
via role stacking (`frappe.session.user == "Administrator"` is explicitly
checked).

This built-in does **not** restrict reading. A user without the modifier role
can still open, print, or list a Sales Invoice dated before the freeze — they
just can't edit or cancel it. That's the actual gap this design fills.

## Premises

1. The built-in freeze fully covers edit/cancel-locking. No new code needed
   there — just configure `Accounts Settings.acc_frozen_upto` +
   `frozen_accounts_modifier`. Agreed.
2. The real scope of this build is **view/read-hiding** before a lock date,
   for a role-gated bypass — not duplicating the edit-lock. Agreed.
3. Frappe's `has_permission` and `permission_query_conditions` hooks are
   looked up as `frappe.get_hooks("has_permission").get(doc.doctype, [])` —
   keyed by exact doctype name at hooks.py load time, no wildcard. There is
   no supported "any doctype, zero code change" hook. **Revised per user
   feedback**: rather than accept a hardcoded-in-hooks.py-only allowlist, the
   design uses a **broad static allowlist wired once in hooks.py**, and
   Rohit Settings' child table lets an admin pick any subset of that
   allowlist to actually enforce — fully dynamic *within* the allowlist.
   Adding a doctype outside the initial allowlist is a 1-line hooks.py change
   (~2 min dev + deploy), the same cost as every other Rohit Settings-driven
   doctype list in this app (`docs_with_pub_att`, `bg_submit_cancel_docs`).
   The alternative — monkeypatching `frappe.has_permission` globally for true
   zero-code-change arbitrary-doctype support — was explicitly rejected: high
   blast radius (every permission check in the Frappe instance, every app),
   no precedent for monkeypatching core in this codebase, and real risk of
   breaking on Frappe upgrades.

## Approaches Considered

### Approach A: Minimal viable
Rohit Settings gets a lock date, a bypass role, and a child table of doctypes
to lock. hooks.py wires `has_permission` + `permission_query_conditions` for
a static allowlist of ~15-20 standard transactional doctypes, all sharing one
handler module (mirrors the existing `core/file.py` → `has_permission["File"]`
pattern already in this app). Covers direct document open/print/API read and
list-view filtering.

Known gap: Frappe's standard financial reports (General Ledger, Trial
Balance, Stock Ledger) run raw SQL against `GL Entry`/similar and do not
automatically respect `permission_query_conditions` — a locked transaction's
amounts could still leak through those reports.

### Approach B: Minimal + report-leak coverage (chosen)
Everything in A, plus explicit lock-date filtering added to the standard
GL-based reports this app already touches (General Ledger, Trial Balance,
Stock Ledger Normal — see recent commits `8be3513`, `d1036b7`, `153ab45`),
so locked-period data can't leak through raw-SQL report paths. Also logs
bypass-role views of locked docs for audit purposes (who used the override
role, when, on what document) — relevant for an accounting-control feature
where "who saw what" is itself a compliance question.

## Recommended Approach

**Approach B.** The report-leak gap in A isn't a hypothetical edge case —
it's the exact mechanism the feature exists to close, sitting one level
below where A stops. Given this app's existing housekeeping around GL-backed
reports (three of the last five commits touch these report files), the
report-layer filtering is a natural, contained extension rather than new
territory. The audit log is small in isolation (one doctype, one insert on
bypass-read) and materially strengthens the "who can see what" story an
accounting-period lock is supposed to tell.

## Open Questions (resolved during eng review — see below)

- ~~Administrator bypass~~ — RESOLVED: Administrator and System Manager are
  both fully exempt from the lock; they are never blocked regardless of the
  bypass role. This is a deliberate departure from `check_freezing_date`'s
  anti-stacking check (which blocks even Administrator on the edit-lock) —
  explicit user call, not an oversight.
- ~~Exact allowlist~~ — RESOLVED: Sales Invoice, Purchase Invoice, POS
  Invoice, Journal Entry, Payment Entry, GL Entry, Delivery Note, Purchase
  Receipt, Stock Entry, Quotation, Sales Order, Purchase Order (12 doctypes).
  Confirmed against live counts on dev-rb-v12 (2026-08-21): Sales Invoice
  70,133; GL Entry 675,373; Journal Entry 52,067; Payment Entry 39,408;
  Purchase Invoice 36,751; Stock Entry 11,053; Delivery Note 7,152; Purchase
  Receipt 5,375; Sales Order 2,453; Purchase Order 1,119. POS Invoice and
  Quotation are 0 today but kept in the allowlist for when the instance
  starts using them. Landed Cost Voucher (0 usage) and Asset (not a
  transaction — no counterparty exchange, doesn't fit the "closed period"
  model) are dropped from launch scope; either can be added later via the
  same 1-line hooks.py change.
- Whether the lock date is a hard cliff or needs a grace-period/warning UX
  before it takes effect (not raised yet — flag if relevant).

## Eng Review Findings (2026-08-21)

**Retention model — RESOLVED.** Not a fixed lock date: a rolling window,
"hide once (today - date_field) > days_to_keep, unless doctype_conditions
holds". This exactly matches an existing pattern in this app —
`Rohit Settings.auto_deletion_policy_for_files` already does
`creation <= NOW() - days_to_keep DAYS AND doctype_conditions` for file
cleanup (`delete_unneeded_files.py:99-109`).

**Child table — RESOLVED, reuse, zero new doctypes for config.** The shared
`Global Search DocType` child table (used by `bg_submit_cancel_docs`,
`docs_with_pub_att`, `auto_deletion_policy_for_files`) is already
custom-fielded with `days_to_keep` (Int) and `doctype_conditions` (Data) —
see `rohit_common/custom/global_search_doctype.json`. A new Rohit Settings
field (e.g. `locked_doctypes`, options: `Global Search DocType`) reuses this
directly. No new child doctype.

**doctype_conditions injection risk — RESOLVED, harden for this use.**
`doctype_conditions` is a raw SQL fragment, string-interpolated
(`delete_unneeded_files.py:104`, `" AND %s" % row.doctype_conditions`) —
an accepted risk for the existing System-Manager-only, scheduled-job
consumer. For this new use (a permission-check codepath, higher-stakes than
a cleanup job), add `validate_lock_conditions()` in
`rohit_common/validations/rohit_settings.py`: a restricted grammar
(`^\w+\s*(=|!=|>|<|is)\s*.+$`) enforced on save. Does not retrofit the
existing file-deletion usage — narrower scope, new consumer only.

**Date field per doctype — RESOLVED.** `Global Search DocType` has no
date-fieldname column. Consistent with the doctype allowlist itself living
in `hooks.py` (not user-configurable — see Premise 3), the
posting-date-vs-transaction-date mapping is a small dict in the shared
handler module, keyed by doctype.

**Audit log — RESOLVED, kept.** New doctype `Transaction Lock Access Log`
(user, document, doctype, viewed_on). Write happens inside the existing
`has_permission` handler on the branch that already fires (bypass-role read
of a locked doc) — not a new trigger point. With Administrator/System
Manager fully exempt, this log's signal is narrow and meaningful: which
non-admin, bypass-role-holding user read closed-period data, and when.

**Report-leak coverage — REVERTED after implementation review (2026-08-21).**
The Role-Permission-restriction approach (System Manager + bypass role only)
was implemented, then reverted: `sync_gl_report_roles()` ran on every Rohit
Settings save regardless of whether locking was active, and *overwrote*
General Ledger/Trial Balance's role list instead of merging into it —
locking ordinary accounting roles (Accounts Manager, Accounts User, etc.)
out of both reports the moment this feature shipped, for all periods, not
just locked ones. Since no lock-aware replacement report was built (the
"replacement report" half of the original plan was never implemented — see
Eng Review Findings below), restricting access was strictly worse than the
gap it was meant to close. **Decision: drop the restriction.** General
Ledger and Trial Balance keep normal, unrestricted ERPNext access. Locked-
period data can still surface through these two reports — a known,
documented gap, same tradeoff Approach A originally had. Per-document
view-hiding (the 12 allowlisted doctypes, via has_permission/
permission_query_conditions) is unaffected and still correct. Stock Ledger
Normal (owned by this app) still gets direct lock-date filtering.

**DocShare bypass — found and fixed (2026-08-21).** Independent adversarial
review found that Frappe's own permission engine ORs an explicit DocShare
grant over whatever has_permission()/permission_query_conditions return
(`frappe.permissions.has_permission` -> `false_if_not_shared()`, and the
shared-condition OR in `frappe.model.db_query.DatabaseQuery`). A document
shared with a user (Desk "Share" button, `frappe.share.add`, or an
auto-sharing workflow) before or after it locks stays visible to that user
regardless of the lock — has_permission never gets a chance to deny it, and
it isn't logged. Fixed via a new daily scheduled task,
`revoke_locked_doc_shares.execute`, that deletes DocShare grants on locked
documents for users who aren't Administrator/System Manager/bypass-role.
This deletes user-created data (shares) as a side effect of a background
job — accepted tradeoff, since the alternative (documenting it as a known
gap) leaves a real, unlogged, zero-effort bypass of the entire feature.

## Final build surface

- `rohit_common/hooks.py` — `has_permission` + `permission_query_conditions`
  wired for the static doctype allowlist, one shared handler module.
- New module: shared lock-check logic (locked/exception/Administrator/System
  Manager/bypass-role branches, per-doctype date-field dict).
- `Rohit Settings` — new fields: `locked_doctypes` (Table, options: Global
  Search DocType), `transaction_lock_bypass_role` (Link, Role).
- `rohit_common/validations/rohit_settings.py` — `validate_lock_conditions()`.
- `stock_ledger_normal.py` — lock-date filtering.
- Role Permission Manager config for General Ledger / Trial Balance
  (data/config, not code) + a lock-aware replacement report or two.
- New doctype: `Transaction Lock Access Log` (audit trail).
- Tests: shared lock-check unit tests, per-doctype permission tests,
  `doctype_conditions` validation tests.

New doctypes: 1 (down from 2). No new child doctype for config (reuse).

## Success Criteria

- A user without the bypass role cannot open, print, list, or find via
  report a locked-doctype document dated on/before the configured lock date.
- A user with the bypass role sees no change in behavior.
- No regression to the existing `Accounts Settings` edit/cancel freeze.
- Adding a new lockable doctype after launch is a single hooks.py + Rohit
  Settings child-table entry, not a schema migration.

## Dependencies

None blocking. Builds on existing `Rohit Settings` single doctype and the
`has_permission` hook pattern already present in `core/file.py`.

## What I noticed about how you think

- You caught that a hardcoded-in-hooks.py doctype list wasn't what you asked
  for ("not to be hardcoded in hooks.py") — that pushback is what surfaced
  the real constraint (Frappe's hook lookup has no wildcard) instead of
  letting a false "dynamic" label slide into the design.
- You picked the report-leak-covering approach over the smaller one without
  needing it explained twice — the instinct that "hidden" has to mean hidden
  everywhere, not just in the obvious places, is the right instinct for an
  accounting-control feature specifically.
